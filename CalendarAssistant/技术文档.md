## 2. 源码分层与 UI

以下短路径均相对于 `app/src/main/java/com/antgskds/calendarassistant/`。

| 层 | 职责 | 主要入口 |
| --- | --- | --- |
| `app/` | 应用运行时、导航、全局 UI 状态、主题 | `app/runtime/AppRuntimeCoordinator.kt`、`app/ui/state/` |
| `feature/` | 业务用例、领域规则、存储和业务 UI | 日程、识别、记账、随口记、便签、天气、备份、云同步等 |
| `platform/` | Android Framework、厂商适配、外部入口、副作用 | 无障碍、通知、悬浮窗、系统日历、短信、Xposed、Widget |
| `shared/` | 读写契约、领域事件、公共组件、管理台账 | `operation/`、`query/`、`event/`、`content/`、`management/` |

包根下的 `App.kt` 负责依赖装配、初始化与订阅，`MainActivity.kt` 是主 Compose 容器。`App.kt` 仍有 `scheduleCenter`、`recognitionCenter` 等历史属性名，实际类型已经使用 `ScheduleFacade`、`RecognitionOrchestrator` 等职责名称。不要新增 `*Center.kt` 或复制一套并行服务。

当前 feature 包括 `accounting`、`appearance`、`backup`、`capsule`、`cloudsync`、`home`、`note`、`notification`、`quickmemo`、`recognition`、`schedule`、`settings`、`update`、`weather`。

业务常按 `application / data / domain / ui` 组织，跨业务契约按需要放 `api` 或 `shared`，小功能不要求创建所有层级。UI 的 `contract` 不依赖具体 ViewModel；`connector` 连接状态与动作，main 中的渲染由 `app/src/native/` host 委托。不要恢复运行时 `UiStyle` 或让 flavor 决定数据库、备份协议和业务规则。

部分迁移过的平台类保留旧 package/FQCN。例如 `platform/entry/legacyservice/image/ImageShareRecognitionWorker.kt` 仍使用 `com.antgskds.calendarassistant.core.service.image`。修改前要检查 Manifest、快捷方式、Worker 持久化类名和系统入口兼容，不能只按物理目录批量改 package。

`:location` 是独立 Android Library，不依赖 `:app`，负责坐标和定位基础能力，天气业务由 `feature/weather` 消费其结果。

## 4. 识别与入库

### 4.1 主动输入

```text
截图 / 图片 → RecognitionApi → RecognitionMultimodalNode → 远程多模态识别
文字 / 语音转写 → RecognitionApi → RecognitionTextNode → 识别模式策略
识别结果 → IngestCommandApi → 日程或账单写入 → 对应反馈
```

独立 OCR 链路和旧文本 AI 配置模式已移除。截图、图片直接交给多模态模型；纯文本输入仍可使用文字能力。图片请求遇到模型不支持多模态时，在本次识别失败反馈中说明，不预先弹出全局提醒。

`MySettings.migrateToMultimodalConfig()` 兼容旧配置，优先保留已有多模态凭据。遗留 `model*`、`useMultimodalAi` 等字段不能仅凭名称删除。

文字和语音转写仍由 `RecognitionModePolicy` 控制：默认仅 AI，也支持日程正则、未命中再 AI、正则入库后 AI 复核。日程正则使用 `RegexScheduleRecognizer` 与 `RegexScheduleRulePrefs`。此策略不改变通知与短信记账“仅本地正则”的约束。

统一 AI 提示词和 JSON 解析位于 `feature/recognition/application/ai/AiPrompts.kt`、`RecognitionJsonParser.kt`。返回结构为：

- `events`：日程与出行、取件等事件分类，不另设 `pickup` 数组。
- `bills`：账单候选。

内部 `AnalysisResult.Success<T>` 定义在 `RecognitionProcessor.kt`，携带 `data`、`bills`、`billIssues` 和 `accountingResult`；最后一项表示实际入库汇总，不能把识别出的候选笔数直接当保存成功笔数。

### 4.2 日程、取件与课程

日程识别结果由 `IngestPipeline → ScheduleIngestWriter` 进入日程门面；日程写入通过 `ScheduleFacade → ScheduleStoreGateway → store` 链路落库。

短信取件使用 `SmsPickupIngestCoordinator`，剪贴板即时码使用 `ClipboardCodeIngestCoordinator`，经 `IngestCommandApi` 入库。它们有自己的本地解析，不需要为了接入统一主流程先调用 AI。

课程配置和映射代码位于 `feature/schedule/domain/course/`，课程与日程结合展示；涉及重复、调课和系统日历同步时应沿用现有映射，不能单独创建另一套课程主库。

## 5. 记账

### 5.1 四类采集入口

| 入口 | 采集与识别方式 | AI 与反馈 |
| --- | --- | --- |
| 主动识别 | 用户输入、截图、选图，经统一识别协议返回账单 | 图像使用多模态；按实际入库结果反馈 |
| 无障碍自动识别 | 支付应用事件、局部 source 与页面树提供信号，等待内容就绪并校验窗口，再截图 | 调用多模态，保留识别进度与结果 |
| Xposed 自动识别 | `PaymentCaptureHook` 采集支付消息，经 `PaymentCaptureProvider` 转发 | 本地 `PaymentMessageParser` / `WechatPaymentParser`，不调用 AI |
| 通知与短信记账 | 通知监听、短信广播、短信数据库兜底，经 `AccountingMessageCoordinator` 提交 | 可编辑本地正则，只显示结果，不调用 AI |

无障碍入口主要位于 `platform/accessibility/TextAccessibilityService.kt`，判断规则集中在 `AutomaticAccountingPolicy`、`PaymentDetailPolicy`、`WechatPaymentSessionPolicy`，节点读取使用 `PaymentWindowReader`。不能将“应用已打开”或单一页面类名直接视为交易成功。识别占用、重复抑制、页面就绪、截图前后前台校验均属于现有流程。

支付应用 Xposed 采集与 SystemUI 小米超级岛 Hook 是不同用途；激活超级岛并不等于已经启用支付应用作用域。Hook 安装成功日志也不代表交易已捕获或入库。

### 5.2 权限和开关

`automaticAccountingEnabled` 是默认关闭的自动记账总开关。通知与短信共用 `accountingMessagesEnabled` 子开关，总开关开启后滑动展开，关闭总开关时关闭子开关。

通知与短信运行必须同时满足总开关、子开关、通知使用权、`READ_SMS` 与 `RECEIVE_SMS`。开启时先跳通知使用权，再申请短信权限；取消或未授权保持关闭，运行与入库前再次核实。通知使用权不是 `POST_NOTIFICATIONS`，后者用于本应用发送通知。

原有 `isSmsMonitoringEnabled` 仅控制取件短信路径，不是记账开关。`SmsReceiver` 合并分段短信，`SmsNotificationListenerService` 读取实际通知正文并跳过组摘要；`SmsContentObserver` 为记账只处理监听会话后的新短信，取件仍保留自己的恢复策略。

### 5.3 规则、去重与保存

`AccountingMessageRules`、`AccountingMessageRulePrefs` 与开发者页的记账规则编辑共用配置。按来源包名或发件人匹配，依次取首条有效规则；金额为必填命名分组，名称、时间和交易号可选。保存后后续消息生效，未知格式静默跳过，不自动调用 AI。首批实际文案和编辑方法见 [通知与短信规则](docs/accounting-message-rules.md)。

所有识别账单仍通过 `RecognitionOrchestrator → IngestCommandApi → AccountingRepository` 保存。正常账单自动入库；明确重复跳过，疑似重复或异常候选暂存。用户可以在疑似重复提示中选择“仍然计入”。去重使用 `AccountingRecognitionMapper`，金额、时间、名称、交易号要结合现有规则解释，不能用测试金额或单一商家补特判。

主动文字缺时间可使用当前时间；历史详情与退款要使用页面提供的时间依据。退款按收入处理，不能把原支出时间直接当作退款到账时间。图片识别账单关联独立截图文件，详情 Sheet 可查看。

### 5.4 导入导出与实测边界

- 微信账单支持 CSV / XLSX，支付宝账单支持 CSV；格式解析位于 `AccountingFileParser`。
- 本应用账单通过 `AccountingBackupCodec` 导出独立 JSON，包含已保存账单及截图。恢复追加、不覆盖已有记录，待确认草稿不包含在账单备份中。
- 编译、正则样本和单测通过，不等于所有系统与支付页面真机通过。已确认场景、诊断证据和未验证范围集中记录于 [自动记账适配与验证](docs/automatic-accounting-testing.md)。

## 6. 数据存储、备份和同步

### 6.1 Room 与设置

主库为 `events.db`，定义在 `feature/schedule/data/db/EventsDatabase.kt`。当前核对版本为 20，后续以源码为准。它承载日程、事件类型与附件、便签、随口记及提醒/建议、账单与待确认账单、WebDAV 同步绑定/修订/资源关系等实体。

Room 是主要业务事实源，Android Calendar Provider 是系统日历互通层。UI、Receiver、Service 不直接写 DAO。数据库迁移必须保留旧数据；19→20 增加账单原图路径，旧记录保持空值，不猜测关联。覆盖升级正常才说明迁移有效，卸载重装不能代替验证。

设置由 `feature/settings/data/SettingsDataSource.kt` 读写 SharedPreferences 的 `settings_json`，模型为 `MySettings`，通过设置读写契约暴露。日程正则与账单消息规则各自有本地规则存储。

附件使用专门表与文件存储，避免塞入描述字段。日程附件、便签附件、随口记音频/图片、账单截图分别由对应业务管理；备份时须按该格式实际支持范围处理。

### 6.2 WebDAV 与本地备份

```text
连接配置 → WebDavConnectionCoordinator → WebDavCredentialStore / KtorWebDavRemoteStore
同步触发 → WebDavSyncV2Coordinator → SyncV2LocalRepository / SyncV2AssetCoordinator → WebDAV
前台触发：WebDavForegroundSyncV2Controller
后台任务：WebDavSyncV2Worker
```

云同步实现位于 `feature/cloudsync`。当前 `SyncV2EntityType` 仅有 `EVENT`、`QUICK_MEMO`，资源角色覆盖日程附件及随口记音频、图片；不能声称账单、便签或所有设置已经自动双向同步。

`BackupCoordinator` 处理应用备份恢复等流程；账单有独立导入导出入口。WebDAV 同步、应用备份、账单备份与系统日历同步是不同能力，修改时分别核对数据范围、身份映射、冲突策略与附件处理。

## 7. 随口记、天气与通知展示

随口记由 `QuickMemoFacade → QuickMemoRepository → QuickMemoDao` 维护，支持文字、语音与图片，并有独立提醒与建议数据。语音入口在 `platform/floating/QuickMemoVoiceCaptureService.kt`。录音、转写、识别与保存不是同一个步骤，排查时区分麦克风权限、前台服务启动和持久化结果。

天气由 `WeatherRepository` 获取天气与位置数据，供 UI、悬浮窗、通知和 Widget 使用，覆盖预报、官方预警与本地风险提示。自动定位需要位置权限，手动选择位置不应被同样的权限条件拦截。

普通通知：

```text
业务 → NotificationApi → NotificationOrchestrator → platform/notification Publisher / Alarm Gateway
```

日程提醒走 `ScheduleNotificationBridge`；旧 `NotificationScheduler` 不用于新增普通提醒。实况通知由 `CapsuleStateManager` 算状态，交 `CapsuleDispatcher` 分流到原生、Flyme 或小米超级岛。原生实况已使用 Google 官方 API，HopOntoIsland 是早期反射方案参考；小米超级岛依赖 SystemUI 跨进程传输，与支付采集作用域分开。

展示模板位于 `shared/management/resource/notification/display/`，只组织展示数据，不写库、不直接调 NotificationManager。Widget 经查询快照与 `WidgetController` 刷新，Renderer 只负责 RemoteViews 展示。

## 8. 注册、权限和诊断

“先登记，再实现”的完整清单见 [AGENTS.md](AGENTS.md)。管理台账分别登记功能、页面、配置、通知类型、流程、工具、策略、Worker；事件规则与调试动作也有独立注册入口。

[build.gradle.kts](build.gradle.kts) 中的架构守卫检查部分代码依赖边界、新增 `*Center.kt`、设置页和通知类型注册。开发者 `registry-check` 检查台账健康；两者不能替代人工检查所有业务边界。不要为通过检查随意放宽 baseline。

普通权限交互复用已有 `PermissionGate` 等工具；通知与短信记账使用串行双权限流程。授权成功后续接用户操作，未授权不写入开启状态，不因生命周期恢复循环弹出权限页。通知读取在取件路径属于兜底，在通知与短信记账路径是必需条件，不能一概当作可选权限。

修改 Activity、Service、Receiver、Provider、Worker 时核对 Manifest、FQCN、R8、PendingIntent 和历史系统入口。支付采集还涉及 `platform/accounting/PaymentCaptureProvider.kt`，不能只核对无障碍 Service。

支付诊断由开发者手动开启 `PaymentAccessibilityDiagnostics` 会话，采集事件、局部节点、多窗口及截图并导出；诊断期间暂停正式无障碍自动识别。普通日志不输出全局 UI 树或财务正文，不把用户诊断包和密钥提交到仓库。

# WebDAV 多设备同步 V2 设计方案

> 状态：首版实现完成，待双设备真实 WebDAV 实机验证。
>
> 日期：2026-08-01

## 1. 背景与结论

现有 V1 使用增量日志、消费游标、快照和日志压缩。实机测试已经出现以下问题：

- 新设备下载远端数据后，可能把远端数据误认为本机历史数据重新上传。
- 删除操作可能被另一台设备保留的旧数据覆盖，导致事件复活。
- 日志压缩后，设备可能进入“需要重新应用快照”但无法自动恢复的状态。
- WebDAV 对共享可变文件、条件写入和锁的兼容性不一致，继续修补 V1 难以保证恢复体验。

V2 不兼容、不迁移也不继续消费 V1 数据。远端使用新的 `sync/v2` 命名空间，核心原则为：

> 不共享可变状态，只交换各设备发布的最终状态。

每台设备只能修改自己的状态文件。其他设备下载这些文件，在本地完成合并。WebDAV 只作为文件交换空间，不承担数据库、事务协调器或冲突裁判职责。

## 2. 范围

V2 第一阶段同步：

- 日程及日程附件。
- 随口记及随口记图片、录音。
- 删除状态和冲突版本。

V2 第一阶段不包含：

- 设置同步和壁纸同步。
- 普通用户自定义远端目录；开发者页保留测试根目录覆盖，系统仍强制追加 `sync/v2`。
- V1 数据迁移和 V1 日志恢复。
- 墓碑及远端资产自动清理。
- 依赖特定 WebDAV 服务端的锁、事务或监听能力。

用户只配置 WebDAV 服务地址、账号、密码和同步密码。应用内部固定生成带版本号的远端目录，避免不同协议版本共用数据。

## 3. 远端目录

```text
WillDo/
└── sync/
    └── v2/
        ├── vault.json
        ├── devices/
        │   ├── {deviceId-A}/
        │   │   ├── device.json
        │   │   └── state.json.gz.enc
        │   └── {deviceId-B}/
        │       ├── device.json
        │       └── state.json.gz.enc
        └── assets/
            ├── {assetKey-1}.bin.enc
            └── {assetKey-2}.bin.enc
```

规则：

- `vault.json` 是创建后不再修改的协议和加密配置，不保存同步进度或最新状态。
- `device.json` 只描述设备 ID、设备名称和协议能力，由所属设备维护。
- 每台设备只能覆盖自己的 `state.json.gz.enc`。
- `assets` 是所有设备共享的不可变资产池。正式资产文件创建后不得修改。
- 删除设备时只能移除对应设备状态，不能连带删除全局资产。

## 4. 设备状态文件

`state.json.gz.enc` 不是操作日志，而是该设备当前本地数据库经过合并后的完整最终状态。它不保存每一次历史操作。

建议的顶层结构：

```text
schemaVersion
deviceId
generation
generatedAt
records
```

- `generation` 只在当前设备成功发布新状态时递增，不跨设备比较。
- 设备通过 WebDAV 的 `ETag` 或修改时间判断其他设备的状态文件是否变化。
- 远端数据合并到本机时，不创建新的业务修订版本，也不刷新业务修改时间。
- 合并改变了本机最终状态后，可以重新发布本设备状态文件，但必须保留原记录的修订信息。内容稳定后不再重复发布。

每条日程或随口记记录至少包含：

```text
syncUuid
revisionId
parentRevisionIds
versionVector
modifiedAt
modifiedByDeviceId
status
payload
attachments
```

- `syncUuid` 是跨设备稳定的数据 ID，不使用 Room 主键或系统日历 `_id`。
- `revisionId` 标识当前修订。
- `parentRevisionIds` 记录当前修订基于哪些版本产生，用于冲突解释和用户解决冲突。
- `versionVector` 用于判断版本先后和并发修改。
- `modifiedAt` 用于展示和诊断，不作为唯一冲突依据。
- `status` 至少包含 `ACTIVE` 和 `DELETED`。
- `payload` 保存日程或随口记的可移植业务数据。

## 5. 本地修订与合并规则

本机用户新增、编辑或删除数据时：

1. 读取该记录已经观察到的版本向量。
2. 当前设备的计数加一。
3. 创建新的 `revisionId`，并记录父修订。
4. 保存业务内容或删除墓碑。
5. 标记本设备状态需要重新发布。

下载其他设备状态后，同一个 `syncUuid` 按以下规则处理：

- 两边修订完全相同：视为重复数据，不执行操作。
- 一个版本向量完整包含另一个：采用较新的版本。
- 较新的版本是墓碑：删除本地可见数据并保留墓碑。
- 旧的正常记录不能覆盖较新的墓碑，禁止数据复活。
- 两个版本向量互不包含：属于并发修改，保留冲突副本，不静默丢弃任意一边。
- 用户解决冲突后创建一个同时继承冲突双方的新修订，使所有设备最终收敛。

所有远端落库操作必须使用专用远端投影入口，并同步更新已观察内容哈希，避免触发本机业务监听后产生新的本地修订。系统日历投影复用现有同步开关，但不伪装成用户手动编辑。

## 6. 墓碑策略

第一版永久保留墓碑，不使用固定 30 天过期规则。

原因：任意设备都可能离线超过 30 天。如果墓碑提前删除，长期离线设备重新上线后可能再次发布旧数据，导致已经删除的日程或随口记复活。

只有未来同时具备以下条件时，才能增加安全回收：

- 可识别仍然有效的设备集合。
- 所有有效设备都确认观察到了对应删除版本。
- 对长期离线设备存在明确的停用或重新初始化规则。
- 清理前可以确认没有仍被引用的冲突分支。

## 7. 全局不可变资产池

附件二进制不写入状态 JSON，也不放在设备目录中。日程附件、随口记图片和随口记录音统一进入全局资产池。

附件关联信息和二进制内容使用不同 ID：

```text
attachmentUuid：某次附件关联的唯一 ID
parentSyncUuid：所属日程或随口记的 syncUuid
assetKey：全局资产池中的内容 ID
```

同一个二进制文件可以被多个 `attachmentUuid` 引用，实现去重，同时保留不同文件名和不同业务归属。

推荐使用以下方式生成远端文件名：

```text
assetKey = HMAC-SHA256(vaultAssetKey, plaintextBytes)
```

相比直接暴露明文 SHA-256，HMAC 仍能在同一同步空间中去重，但不会让远端观察者使用公开文件哈希反查内容。

状态中的附件元数据至少包含：

```text
attachmentUuid
parentSyncUuid
assetKey
fileName
mimeType
plainSize
plainSha256
```

状态文件本身已加密，因此 `plainSha256` 不会直接暴露在远端目录名中。

## 8. 资产上传与下载

上传必须先完成资产，再发布引用它的状态：

1. 计算 `assetKey`。
2. 检查 `assets/{assetKey}.bin.enc` 是否已经存在。
3. 不存在时，将加密结果上传为同目录内带设备 ID 和随机上传 ID 的临时文件。
4. 上传完成后校验长度和加密封装完整性。
5. 使用同目录 `MOVE` 原子发布为正式文件。
6. 如果并发上传导致正式文件已经存在，删除本机临时文件并验证已有正式文件。
7. 只有正式资产可用后，才能发布引用它的设备状态。

AES-GCM 使用随机 nonce，因此相同明文产生的密文字节不保证相同。并发上传时无论最终保留哪一份完整密文，只要它能通过认证、解密后匹配明文哈希，即可视为同一资产。

下载流程：

1. 合并状态并找出本机缺少的 `assetKey`。
2. 下载到本地临时文件。
3. 完成 AES-GCM 认证、解密和明文 SHA-256 校验。
4. 原子移动到应用管理的本地附件目录。
5. 通过 `attachmentUuid` 和 `parentSyncUuid` 建立业务关联。

正文数据可以先完成合并和 UI 刷新。附件下载失败时记录为“等待下载”并在后续同步中重试，不能删除附件元数据，也不能回滚已经成功合并的正文。

第一版不自动删除远端资产。未被引用的资产只会占用空间，不会造成数据错误；过早删除则可能造成不可恢复的数据丢失。

## 9. 原子发布与失败恢复

设备状态发布：

```text
PUT  devices/{deviceId}/state-{uploadId}.tmp
MOVE devices/{deviceId}/state-{uploadId}.tmp
  -> devices/{deviceId}/state.json.gz.enc
```

临时文件和正式文件必须位于同一目录，避免部分 WebDAV 服务不支持跨目录 `MOVE`。

失败处理：

- 临时文件上传失败：保留本地待发布状态，下次完整重试。
- 临时文件上传成功但 `MOVE` 失败：正式状态仍是上一完整版本，下次重新发布。
- 下载到半文件或解密失败：不修改本地数据库，保留上一次成功读取的 `ETag` 和状态。
- 某台设备状态损坏：只影响读取该设备的新状态，不阻塞其他设备状态的合并。
- 附件失败：标记资源等待重试，不阻塞正文数据刷新。

## 10. 一次同步的固定顺序

1. 校验固定远端目录和 `vault.json`。
2. 扫描本机 Room 变化并生成本机修订。
3. 先上传本机状态将引用的缺失资产，防止并发合并替换可见分支后遗漏附件。
4. 通过 `PROPFIND` 发现设备目录，按 `ETag` 下载并验证发生变化的设备状态。
5. 在 Room 事务中按 `syncUuid` 和版本向量合并，并立即刷新正文 UI。
6. 保存已经成功解密并合并的设备 `ETag`；附件失败不要求重复下载同一状态文件。
7. 下载当前可见版本缺少的附件，单个附件失败时保留等待状态供下一轮重试。
8. 再次扫描本机，吸收合并期间产生的业务变化并上传剩余资产。
9. 生成本设备当前完整最终状态，业务修订信息保持不变。
10. 原子发布本设备状态文件，仅在发布成功后保存本机发布代数与状态哈希。

前台同步和 WorkManager 后台同步必须共用同一个进程内互斥入口，避免本机同时运行两个同步事务。本地用户在同步期间产生的新修改不丢失，未进入本次一致性读取的修改留到下一轮发布。

## 11. 首次接入与设备生命周期

第一台设备：

1. 创建或读取不可变的 `vault.json`。
2. 为当前安装生成持久化 `deviceId`。
3. 为现有日程和随口记补充 `syncUuid` 和初始版本。
4. 先上传资产，再发布本设备完整状态。

后续设备：

1. 保存开启同步前的本机数据集合。
2. 校验同步密码和 `vault.json`。
3. 下载所有已有设备状态并本地合并。
4. 为仍然只有本机存在的数据建立版本。
5. 对没有 `syncUuid` 的疑似重复日程，可使用标题、开始时间、结束时间等进行首次启发式绑定；无法确定时保留两条，不能误删。
6. 发布本设备合并后的完整状态。

设备报废或被停用后，其他设备已经发布的完整状态仍可保留其业务数据。删除设备目录不等于删除日程、随口记或资产。

## 12. 加密要求

- 所有状态和附件内容使用同步密码派生的密钥进行 AES-GCM 加密。
- `vault.json` 只保存协议版本、KDF 参数、随机盐和密钥校验信息，不保存同步密码或可直接使用的明文密钥。
- 每个加密文件使用独立随机 nonce。
- 状态解密成功后仍需验证结构版本和业务数据约束。
- 附件解密成功后验证明文长度与 SHA-256。
- 使用错误同步密码的设备必须在上传任何状态或资产前失败。

## 13. V1 处理原则

- V2 使用独立远端目录，不读取 V1 游标、日志、快照或资产索引。
- 不自动删除 V1 远端文件，避免测试期间误删用户数据。
- 当前只有开发者测试设备使用 V1，可由开发者在确认 V2 可用后手动清理测试目录。
- V2 入口完成后，旧协调器、日志压缩和快照追赶流程停止被业务调用；源码清理在 V2 验证通过后单独进行。

## 14. 实施前检查项

正式编码前先完成以下审计，不改变现有同步行为：

- 列出 V1 中可直接复用的 WebDAV 请求、认证、目录创建和同目录 `MOVE` 能力。
- 核对现有加密封装能否支持独立文件随机 nonce、流式附件和 HMAC 资产键。
- 核对日程、随口记和附件是否都具备稳定 `syncUuid`，并找出仍使用本地数据库 ID 的关联。
- 盘点所有本地新增、编辑、删除入口，确认能够统一创建本地修订并标记来源。
- 确认远端落库路径可以携带 `REMOTE_SYNC`，且不会触发同步回环。
- 确认 Room 可以在一个事务中写入业务数据、版本向量、墓碑和冲突副本。
- 定义 UI 刷新信号，确保远端落库完成后立即刷新列表。
- 定义附件的本地缓存状态和失败重试状态，避免资源失败阻塞正文同步。
- 为 Native 和 HyperOS 共用同一同步业务实现，UI 只读取统一状态。

## 15. 最低验证矩阵

使用两台设备和全新 V2 远端目录验证：

- A 新增，B 拉取。
- A 编辑，B 拉取；B 再编辑，A 拉取。
- A 删除，B 拉取，随后双方多轮同步均不复活。
- A、B 离线修改不同记录，恢复网络后自动合并。
- A、B 离线修改同一记录，产生冲突副本。
- A 离线删除、B 离线编辑同一记录，进入可解释冲突而不是静默丢失。
- 日程附件、随口记图片和录音上传、下载、重试及去重。
- 上传状态或附件中途断网，下一轮能够恢复。
- 清空全新测试目录后重新初始化。
- 停用一个设备目录后，其他设备的数据和全局资产仍然可用。
- 前台 1 至 300 秒同步与后台 15 分钟同步不并发执行。

## 16. 实施决策摘要

V2 的固定边界如下：

- 可变状态按设备物理隔离。
- 每台设备发布完整最终状态，不发布无限增长的操作日志。
- 冲突合并在本地执行，时间戳不作为唯一依据。
- 删除使用永久墓碑，旧状态不能复活数据。
- 资产进入全局不可变内容池，业务状态只保存资产引用。
- 资产先于状态发布，所有文件通过临时文件和同目录 `MOVE` 原子落地。
- 设置同步继续关闭。
- V1 不兼容、不迁移、不继续修补。

# 2026-08-02 开发计划：彩云天气可选数据源接入

## 一、计划状态

当前状态为：**已启动，代码接入完成，等待编译与实机验证**。

2026-08-02 已确认采用“和风天气 / 彩云天气”可选数据源方案，凭证均由用户自行配置。

## 二、背景与结论

当前天气功能实际只支持和风天气。虽然 `MySettings` 已有 `weatherProvider` 字段，但设置页、`WeatherRepository` 和请求 URL 仍固定使用 `qweather`。

截至 2026-08-02，彩云官方公开资料没有承诺永久免费 API 套餐。公开套餐以按量、包月和企业计费为主，因此彩云天气只能作为用户自行配置凭证的可选数据源，不能替代和风天气成为默认服务，也不能在开源 APK 中内置公共 Token。

官方资料：

- API 文档：<https://docs.caiyunapp.com/weather-api/index.html>
- 认证说明：<https://docs.caiyunapp.com/weather-api/auth.html>
- 计费说明：<https://docs.caiyunapp.com/weather-api/billing.html>
- 开放平台：<https://platform.caiyunapp.com/api/manage?mode=weather>

## 三、目标与非目标

### 3.1 目标

1. 保留和风天气为默认 Provider，现有用户升级后行为不变。
2. 在天气配置页允许用户选择“和风天气”或“彩云天气”。
3. 用户自行填写对应 Provider 的凭证，不由 WillDo 代付或转发请求。
4. 将不同供应商响应统一映射为现有 `WeatherData`、`WeatherAlertData` 和预报模型。
5. 复用现有缓存、后台刷新、官方预警、本地天气风险、通知、小组件和天气详情页。
6. Provider 切换失败时保留原配置和缓存，不破坏现有天气功能。

### 3.2 非目标

- 不建设中转服务器或共享凭证服务。
- 不在 APK、源码、CI 或远程配置中保存彩云公共 Token。
- 不自动替用户购买套餐或注册彩云账号。
- 第一版不同时重做天气页面 UI。
- 第一版不引入彩云地图、雷达图和历史天气等当前产品没有消费入口的数据。
- 不在没有真实账号的情况下宣称完成彩云实机兼容验证。

## 四、当前代码需要先解决的边界

当前关键链路：

```text
WeatherSettingsPage
  -> MySettings
  -> WeatherRepository
  -> WeatherApiAdapter
  -> WeatherData
  -> 通知 / 小组件 / 天气详情页
```

现状中的 Provider 耦合点：

- `WeatherSettingsPage` 保存时强制写入 `WeatherApiAdapter.PROVIDER_QWEATHER`。
- `WeatherRepository` 分别请求和风的实况、24 小时、7 天和预警接口。
- 请求使用和风专用的 `X-QW-Api-Key` Header。
- `WeatherApiAdapter` 只解析和风 JSON。
- `hasWeatherConfig()` 默认要求和风 URL 和 Key。

因此不能直接在现有请求方法中堆叠 `if (provider == ...)`。应先建立 Provider 边界，再接入彩云实现。

## 五、建议架构

### 5.1 Provider 标识

保留字符串持久化以兼容设置备份：

```text
qweather
caiyun
```

非法值统一回退到 `qweather`，已有用户无需迁移。

### 5.2 Provider 客户端

建议新增天气数据源接口：

```kotlin
interface WeatherProviderClient {
    val providerId: String

    suspend fun fetch(
        settings: MySettings,
        location: WeatherLocation
    ): ProviderWeatherPayload
}
```

实现：

- `QWeatherProviderClient`：搬移现有和风请求，第一阶段必须保持行为不变。
- `CaiyunWeatherProviderClient`：调用彩云综合天气接口。

`WeatherRepository` 只负责：

1. 解析和稳定位置。
2. 按 `weatherProvider` 选择客户端。
3. 接收统一结果并写缓存。
4. 运行现有 `WeatherRiskAnalyzer`。
5. 分发通知和刷新 UI。

### 5.3 统一载荷

Provider 客户端返回统一载荷：

```text
current
hourlyForecast
dailyForecast
officialAlerts
attributions
minutelySummary（可选）
```

第一版仍以现有 `WeatherData` 为事实模型。只有彩云分钟降水确实有 UI 消费入口时，才新增对应字段，避免为了完整映射扩大数据库和界面范围。

## 六、彩云接口与数据映射

彩云 v2.7 综合接口可一次返回实况、小时、逐日、分钟降水和预警。本轮已按实际响应完成字段核对和解析。

当前参考格式：

```text
GET https://api.caiyunapp.com/v2.7/{credential}/{longitude},{latitude}/weather
```

映射原则：

| WillDo 数据 | 彩云数据 |
| --- | --- |
| 当前温度、体感温度 | `realtime.temperature`、`realtime.apparent_temperature` |
| 天气现象 | `realtime.skycon` |
| 湿度、气压、能见度 | `realtime.humidity`、`pressure`、`visibility` |
| 风向和风速 | `realtime.wind` |
| 小时预报 | `hourly` |
| 每日预报 | `daily` |
| 官方预警 | `alert.content` |
| 分钟降水摘要 | `minutely.description`，第一版可只缓存或暂不展示 |

注意事项：

- 彩云坐标顺序是“经度,纬度”，不得与常见的“纬度,经度”混淆。
- 请求必须使用 `WeatherLocation` 中解析后的坐标，不能把和风 Location ID 直接传给彩云。
- `skycon` 需要单独映射到现有天气图标和中文文案。
- 预警等级、颜色、发布时间和解除状态必须统一映射到 `WeatherAlertData`，继续复用 `WeatherWarningText`。
- 彩云已经返回的官方预警继续参与现有风险分类去重，避免官方预警与本地推断风险重复通知。

## 七、配置页方案

天气配置页增加数据源选择：

```text
天气数据源
[和风天气 / 彩云天气]
```

和风天气字段：

- API Host
- API Key

彩云天气字段：

- 官方要求的 App Key / App Secret，或实施时仍受支持的 Token
- API Host 默认使用官方地址，不建议普通用户修改

交互规则：

1. Provider 切换只修改页面草稿，点击“连接”成功后才保存。
2. 连接测试必须请求真实接口并验证关键字段，不能只检查 HTTP 200。
3. 凭证输入默认以圆点遮挡，聚焦或点击查看后显示明文，行为与模型配置页一致。
4. 错误提示区分认证失败、额度不足、限流、网络失败、坐标错误和响应格式变化。
5. 不把彩云凭证写入日志。
6. App Secret 或同步密码级别的敏感字段应进入本地加密存储，并排除设置同步与普通备份；实施时同时评估现有天气 Key 的存储方式是否需要统一升级。

## 八、缓存、切换与兼容策略

- 缓存中记录 `providerId`，避免切换 Provider 后继续展示旧供应商数据却误认为刷新成功。
- 切换成功后清理或隔离旧 Provider 天气缓存，但不删除旧凭证，便于用户切回。
- 后台 `WeatherSyncWorker` 继续读取统一配置，不为彩云增加第二套调度器。
- 网络失败时可以展示同 Provider 的未过期缓存，不能跨 Provider 静默回退。
- 不自动从和风配置迁移到彩云配置。
- 设置备份导入旧版本数据时，缺少 Provider 仍回退到 `qweather`。

## 九、分阶段实施顺序

### 阶段 0：启动前确认

- 确认用户需求不是单个临时建议。
- 准备合法彩云开发账号和测试凭证。
- 再次确认价格、授权范围、署名要求、限流和接口版本。

### 阶段 1：Provider 边界重构

- 提取 `WeatherProviderClient`。
- 将现有和风请求迁移到 `QWeatherProviderClient`。
- 保持设置页和用户行为完全不变。
- 先完成和风回归测试再继续。

### 阶段 2：彩云解析与 Mock 测试

- 增加彩云响应 DTO 和适配器。
- 使用脱敏 JSON fixture 覆盖实况、小时、每日、预警和空字段。
- 使用 Ktor `MockEngine` 验证认证失败、限流、超时和畸形响应。

### 阶段 3：配置页接入

- 增加 Provider 选择和动态凭证输入。
- 增加连接测试。
- 处理 Provider 缓存隔离和切换回滚。

### 阶段 4：真实服务验证

- 在至少一台设备上验证前台刷新和后台 Worker。
- 验证官方预警、本地风险去重、通知、小组件和详情页。
- 记录实际调用量，确认刷新频率不会造成不必要费用。

### 阶段 5：发布准备

- 补充用户配置说明和费用提示。
- 检查 APK、日志、备份和 WebDAV 状态文件中不存在测试凭证。
- 确认彩云署名及数据展示符合官方授权条款。

## 十、测试清单

### 自动测试

- Provider 非法值回退。
- 和风 Provider 重构前后响应一致。
- 彩云 `skycon`、风、温度、湿度和预报映射。
- 彩云预警新增、更新、解除状态映射。
- 空预警、空小时、空逐日数据。
- 401/403、额度耗尽、429、5xx、超时和无网络。
- Provider 切换后的缓存隔离。
- 旧设置和旧备份兼容。

### 实机测试

- 手动位置与自动定位。
- 前台刷新和后台定时刷新。
- 首页天气、详情页、天气小组件。
- 官方预警和本地天气风险通知。
- 深浅色模式及配置页凭证显示/隐藏。
- 无套餐、额度耗尽和凭证撤销后的错误提示。

## 十一、验收标准

只有同时满足以下条件，才能认为彩云天气接入完成：

1. 现有和风用户升级后无需重新配置且行为不变。
2. 彩云连接测试、前台刷新和后台刷新均通过真实服务验证。
3. 主要天气字段、小时/每日预报和官方预警正常展示。
4. 通知、小组件和本地风险分析不依赖具体 Provider。
5. Provider 切换失败不会覆盖可用配置。
6. 源码、APK、日志、备份和同步数据中不存在开发测试凭证。
7. 配置页不预填任何彩云 Token。

## 二、阶段目标

本阶段最初不是一次单纯的目录移动，而是一条连续架构线：

```text
功能稳定性修补
  -> UI 与业务边界整理
  -> 设置页和页面 contract 化
  -> UI edition 从运行时切换改为构建期 flavor
  -> Center / legacy 顶层包清理
  -> 目录按职责归并
  -> Debug 双 flavor 可构建验证
```

最终目标：

1. 保持当前 App 可编译、可安装、可继续修用户反馈问题。
2. 把后续 HyperOS 风格版本需要的边界提前整理出来。
3. 不再让旧 `core/data/calendar/store/ui/service` 顶层目录继续扩散。
4. 把新增业务收敛到 `feature`，系统副作用收敛到 `platform`，公共契约收敛到 `shared`。
5. 用架构护栏防止重构后目录再次回流。

## 五、2026-07-11：定位模块、UI flavor 与设置页 contract 化

### 5.1 `:location` 独立模块

7 月 11 日开始将定位拆出为独立模块：

```text
:location
```

设计原则：

- `:location` 不依赖 `:app`。
- `:location` 只提供设备定位契约和 Android 定位实现。
- 天气模块消费定位结果，但定位模块不包含天气业务。

该拆分为后续基于定位扩展功能提供边界。

### 5.2 引入 `native` / `hyperos` product flavors

本阶段明确放弃“软件内运行时切换原生/HyperOS 风格”的方向，改为构建期版本：

```text
nativeDebug / nativeRelease
hyperosDebug / hyperosRelease
```

主要原则：

- 同一个应用包名。
- 共享业务、数据库、备份、通知协议。
- UI 风格差异只放在 flavor host / renderer。
- 不恢复运行时 `UiStyle` 或旧 `miui` 包。

### 5.3 设置页和功能页逐步 contract 化

7 月 11 日一系列提交将设置页和功能页逐步放到 UI contract / connector / flavor host 后面：

- About
- WeatherDetail
- AppUpdate
- CourseManager
- ScheduleSettings
- Archives
- RegexRules
- Donate
- ConfigEditor
- ScheduleColors
- BottomBarEditor
- Laboratory
- ThemeSettings
- AI Settings
- TimeTableEditor
- WidgetSettings
- WeatherSettings

目的：

1. 让 main 层保存 UI 状态和业务连接。
2. 让 flavor host 只负责选择外观，不直接持有具体 ViewModel 和 Repository。
3. 为后续 HyperOS 风格替换提供入口。

- 删除损坏的拆分 renderer。

后续处理原则：

- 不再用 `Set-Content` 批量重写 Kotlin 源码。
- 需要写源码时优先用 `apply_patch`。
- 含中文文件必须注意 UTF-8 编码。

## 十、关键决策记录

### 10.1 不再做软件内风格切换

原本曾讨论在软件内提供 MIUI/HyperOS 风格切换。最终方向改为：

```text
native flavor
hyperos flavor
```

原因：

- 降低包体和运行时复杂度。
- 避免业务层根据 UI 风格分支。
- 后续可以分别优化原生版和 HyperOS 版。

### 10.2 不直接引入完整 MIUIX

调研后发现当前 MIUIX 源码对 Kotlin、Compose Multiplatform、AGP 等版本要求较高。直接引入会带来较大升级成本。

当前结论：

- 可参考 MIUIX / HyperCeiler 的视觉和交互。
- 不直接把完整源码作为当前主线依赖。
- HyperOS 风格优先在自身 renderer/host 层实现。

### 10.3 保留 legacy FQCN

部分物理路径已经迁移，但 package 不改：

```text
com.antgskds.calendarassistant.core.service.*
com.antgskds.calendarassistant.calendar.jobs
com.antgskds.calendarassistant.calendar.receivers
```

原因是它们可能被 Manifest、快捷方式、系统调度、PendingIntent、历史组件名引用。

### 10.4 先完整迁移再集中编译

本次大迁移中采用“先做完整迁移，再集中编译修复”的策略。

原因：

- 目录迁移期间逐步编译会被中间态错误拖慢。
- 大批包名移动更适合一次性收敛后统一修 import。
- 最终以 Debug 双 flavor 构建和架构护栏作为完成标准。

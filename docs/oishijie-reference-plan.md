### 1. 搜索／选图重复触发

**我们的现状：** `HomeScreen` 的 `searchRequestId`、`imageRequestId` 在点击时递增；`HomePage` 用 `LaunchedEffect` 处理非零请求，处理后未消费或清除。若承载这些效果的页面退出组合后重新进入，而上层仍保留旧 ID，旧请求可能再次执行。普通重组不等于必然重放，也没有真机复现证明某次切页一定触发此问题。

**fork 的处理：** 页面处理请求后调用 `onRequestsHandled`，上层将两个 ID 清零；切页相关入口也清理请求。参考的是“一次请求只消费一次”的思路。

**后续预期：**

- 展开搜索后，用户退出搜索，再进入页面时不因已处理的旧请求自动展开。
- 点“上传图片识别”后打开选图界面，取消或选图完成后不因旧请求再次打开。
- 用户主动再次点击时仍能正常搜索或选图。
- 搜索与选图分别消费；处理一个请求时不能误删另一个尚未处理的新请求。
- 离开目标页面时不把一次性操作留待用户之后返回页面再执行。
- 请求消费只处理入口触发，不改变搜索内容、图片识别或入库流程。

**操作例子：** 点击上传图片识别 → 相册打开 → 取消 → 离开并返回日程页。预期相册保持关闭，直到用户再次主动点击。

### 2. 震动开关修复

**我们的现状：** 已有 `hapticFeedbackEnabled` 和“触感反馈”设置。明确传入设置的组件已受控；无参数 `rememberAppHaptics()` 读取 `LocalAppHapticsEnabled`，默认值为 `true`。偏好设置页已有局部提供，但主界面和悬浮窗缺少统一根级提供，部分底栏、菜单等交互仍可能震动。

**fork 的处理：** 在 `MainActivity` 根部提供真实设置；悬浮窗是独立窗口，另行提供同一开关。

**后续预期：**

- 复用已有开关，不新增第二个震动开关。
- 主界面、底栏、菜单、应用弹窗和悬浮窗中的应用触感读取一致的设置。
- 设置改变后，已显示的主界面和悬浮窗也更新，不要求重启。
- 检查相关直接触感／震动调用是否绕过开关，补齐实际遗漏。
- 本项作用于应用交互反馈；日程提醒的通知震动及系统键盘反馈仍按各自设置处理。

**操作例子：** 关闭“触感反馈”后，切换底栏、长按菜单、操作悬浮窗不再产生应用交互震动；重新开启后恢复。

### 3. 日历视图记忆

**我们的现状：** `calendarViewName` 使用 `rememberSaveable`，已有页面状态保存与恢复，但没有日历视图类型的长期偏好存储。没有恢复状态的新启动默认今日视图，宽屏根据可用模式适配。

**fork 的处理：** 增加“记住日历视图”开关与持久字段，在用户选择视图时写入设置。它没有保留我们的课表和宽屏视图规则，不能直接照抄枚举或布局。

**后续预期：**

- 记忆的是今日／周／月／日程等视图类型，不包含上次选中的日期或滚动位置。
- 持久设置与现有页面状态恢复各司其职；旋转、临时切页和从后台返回时，不反复套用启动规则导致跳视图。
- 保留当前手机与宽屏的可用模式，并处理课表模块关闭等情况。
- 区分用户主动选择和系统因布局／模块变化执行的临时回退，避免临时回退随意覆盖用户偏好。
- 设置读到旧值、未知值或当前不可用模式时安全回退，不崩溃、不清理用户数据。

当前源码中的视图范围：

| 布局 | 可用视图 |
| --- | --- |
| 手机单栏 | 今日、周、月、日程 |
| 宽屏双栏 | 周、月、课表；课表受模块开关约束 |

**操作例子：** 启用记忆后，用户主动切到月视图，结束应用并重新启动，日历恢复月视图。上次选中的是哪个日期不属于本项的长期记忆范围。

## 五、下一代随口记方向与分阶段范围

### 已讨论的产品方向

1. **识屏收藏：** 在抖音、哔哩哔哩、公众号、小程序内容页等场景，截图并尝试获取当前内容原链接，上传截图供 AI 分析，收藏到随口记。发现日程／取件码时询问是否创建对应记录，避免抖音聊天记录等页面丢失识别能力。
2. **普通识屏：** QQ、微信聊天、短信等场景，沿用日程／取件码截图识别用途。微信内的公众号、小程序和聊天需结合页面信息判断，不能只按包名分流。
3. **分享兜底：** 软件支持系统分享时，可将链接、选中的文字或图片分享到随口记。没有链接也应保留用户分享的文字，长按 → 全选／选择片段 → 分享即可满足文字收藏。
4. **原内容回跳：** 有原链接的随口记，在详情页底部 toolbar 右侧单独显示圆形“→”按钮，用于打开原内容。
5. **文件夹：** 允许创建文件夹；顶部“全部删除”按钮替换为 list 按钮，用于创建和选择文件夹、筛选列表。
6. **默认列表：** 默认显示全部随口记，不记忆上次文件夹筛选；退出后重置筛选与选择状态。
7. **多选管理：** 长按条目由原浮动操作卡改为进入选择模式；选择模式下底部显示“移动至”“删除”工具栏。

上述为产品方向，分阶段实现。用户目前提出先落地基础改善、文字分享和链接探针；AI 摘要明确留到后续，不一次完成所有功能。

仍待明确的产品细节：从文件夹打开随口记详情再返回列表时，是否也恢复“全部”；单层文件夹／一条记录一个文件夹属于本轮建议，尚未作为用户确认的规则。

### 第一阶段文字分享的行为

- 在系统分享菜单提供“保存到 Will do 随口记”文字目标，支持纯文字及包含链接的分享文案。
- 完整保留实际收到的文字和换行。没有链接不是失败条件；此阶段链接先作为正文的一部分保存，不要求独立来源字段或跳转按钮。
- 保存成功后提示完成并返回原软件，不要求打开主界面或先选择文件夹。
- 复用现有图片随口记入口和现有随口记存储，不导入另一套闪记／便签数据模型。
- 分享路径先做纯保存，不自动生成摘要，也不因为收藏了一段文字就后台触发日程候选分析；既有其他入口的识别行为保留。
- 当前 `QuickMemoFacade.createTextMemo` 对非空正文会调用 `analyzeTextForSuggestions`。实施时需要在统一创建能力／对应策略中明确分享来源的行为，不能直接调用现有默认路径后误以为只是保存，也不能由分享 UI 直接写 DAO。
- 按软件实际提供的系统分享数据处理；优先兼容文本 `ACTION_SEND`，选中文字的 `PROCESS_TEXT` 是否同时接入按实际目标与入口设计确定。
- 用户选中的文字可能仅是文章片段；接收端保存提供的原文，不凭片段宣称已保存整篇文章。

## 六、第一阶段链接探针计划

### 用途与入口

探针是开发者可见的调试工具，只负责记录证据。需要回答两个问题：

1. 无障碍、近期系统日志中能否取得当前内容可用于回跳的原链接？
2. 前台 Activity 或节点特征能否区分公众号文章、小程序、聊天等页面类型？

在开发者页面提供主动的“开始链接探针”“结束并导出”动作。用户先开始会话，再进入目标软件／小程序并切换待测内容；结束后导出本地报告。探针不调用 AI、不创建日程或随口记、不自动操作分享／复制按钮，也不在本阶段接入正式识屏收藏或建立完整页面分流功能。

只在主动开启的诊断会话中采集，结束、超时或服务终止后停止。会话时长、采样与记录上限实施前登记 `ConfigCatalog`，调试动作登记 `DebugActionRegistry`，对应新增能力按 `AGENTS.md` 登记。

### 目标场景

采样范围为抖音、哔哩哔哩、微信、小红书、浏览器等明确指定的目标软件。微信需分别测公众号文章页、小程序页、聊天页。同一场景采集多个样本，支持连续切换内容的对照。

进入非目标软件时暂停目标内容采样，不读取并保存非目标页面的节点树或链接内容。Will do 自身、控制中心、系统分享菜单等界面不能代替待测内容页。

### 三路信息与时间对齐

| 来源 | 采集重点 | 需要报告的实际状态 |
| --- | --- | --- |
| 无障碍节点树 | 节点层级、文字、contentDescription、控件 ID、可见性、可点击状态及动作；地址栏和节点中实际出现的 URL 候选 | 服务不可用、节点不可读取、采集被截断、读取成功但未发现链接、发现候选。 |
| 近期系统日志 | 当次采样时间范围内的目标应用及相关系统记录，保留 URL 候选、日志自身时间、tag／进程等来源上下文 | 当前权限方式、日志读取失败／受限、可读但未发现链接、发现候选。 |
| 前台页面信息 | 当前前台包名、窗口、真实 Activity 名及获取来源；无障碍事件 className 单独记录 | 读取成功、读取受限／失败、Activity 未知、采样期间前台页面发生变化。 |

每组样本使用同一个会话 ID、采样 ID 和采样基准时间，将三路结果关联起来。记录采样开始／结束时间，并保留各来源自己的实际观察时间；三路读取不是原子操作，采样期间页面变化应在报告中标记。

日志的“原记录时间”与探针的“读取时间”分别保存。不能把旧日志中的 URL 因为本次刚读取到，就当成本次新页面产生的链接。

### 采集实现边界

- 使用现有无障碍服务，读取当次目标页面。地址栏依实际节点信息寻找，不假定所有浏览器或内置网页都暴露完整 URL。
- 系统前台 Activity 信息可在现有权限允许时通过系统任务／窗口信息尝试读取。保留获取方式、读取时间和失败状态；拿不到时写“未知”。
- `AccessibilityEvent.className`、节点 className 可能是控件类名，不一定是 Activity 名。字段分开保存，不把控件类名冒充已确认的前台 Activity。
- 复用已有 root／Shizuku 特权进程能力。普通权限只能读到部分日志时，明确标为能力受限；有 root／Shizuku 也以实际读取结果为准。
- 当前 `DiagnosticLogExporter` 主要按 Will do 自身 UID／PID 过滤。直接导出它的日志不能验证目标应用链接；探针需按自己的目标与时间范围采样，并覆盖相关系统打开页面记录。
- 参考现有主动诊断的生命周期与导出方式，保留独立用途，不直接搬入支付诊断专用规则或截图循环。
- 节点／日志中的真实 URL 作为候选保存。内容标题、作者、软件包名或 Activity 名本身不能证明原链接。
- 页面类型记录为候选及其依据，无法判断时写“未知”。结合实际测试场景复盘，不仅凭微信包名或 Activity 名直接认定页面类型。
- 完整链接和必要诊断上下文保存在主动会话的本地报告，不混入普通业务日志。

### 输出与复盘

导出结构化 JSON／JSONL 和便于直接阅读的文本摘要。三路信息关联在同一组样本中，至少包含：

- 会话 ID、采样 ID、采样时间和各来源实际观察时间。
- 前台包名、Activity 名、Activity 获取来源、窗口及独立的无障碍事件 className。
- 候选页面类型、判断依据，以及未确认／未知状态。
- 候选链接及来源：节点文字、节点描述、地址栏或系统日志。
- 对应的节点／日志上下文，日志原记录时间，以及权限、失败、截断和页面变化状态。
- 原链接与当前内容的对应关系，初始记为待核对，不因发现 URL 就标记成功。

广告、统计、封面、视频资源地址与之前打开过的内容链接不能直接当作当前内容的回跳链接。报告应允许比较连续样本中各路链接是否变化、是否持续停留在旧内容，以及哪一路能稳定对应当前内容。

### 实际验证

1. **抖音：** 连续刷十个视频，每个视频采样，检查候选链接是否随当前内容更新；补测抖音聊天页面。系统日志是否保留旧链接需要通过样本确认。
2. **哔哩哔哩：** 不同视频／文章页分别多次采样，核对链接与当前内容。
3. **微信：** 公众号文章、小程序、聊天页分别多次采样，对比 Activity、事件 className 和节点特征，判断是否能区分页面类型。
4. **小红书：** 连续切换不同笔记／视频内容，检查链接及页面信息的对应关系。
5. **浏览器：** 不同网页分别多次采样，检查地址栏、节点和日志能提供什么。
6. **能力与结束行为：** 检查“未找到链接”和“无权限／采集失败”是否分开报告；离开目标软件时是否暂停，结束后是否停止采样并正常导出。

## 二、参考来源与实施前事实

参考仓库：[oishijie/Will-do](https://github.com/oishijie/Will-do)。

已对比的源版本：`830b65febde8609f99158f2a68fadc3bb4c3add9`。

以下内容保留本轮实施前的源码差异，不能代表实施后的现状；当前第一阶段行为见第七节。

### 1. 搜索／选图重复触发

**实施前：** `HomeScreen` 的 `searchRequestId`、`imageRequestId` 在点击时递增；`HomePage` 用 `LaunchedEffect` 处理非零请求，处理后未消费或清除。若承载这些效果的页面退出组合后重新进入，而上层仍保留旧 ID，旧请求可能再次执行。普通重组不等于必然重放，也没有真机复现证明某次切页一定触发此问题。

**fork 的处理：** 页面处理请求后调用 `onRequestsHandled`，上层将两个 ID 清零；切页相关入口也清理请求。参考的是“一次请求只消费一次”的思路。

**后续预期：**

- 展开搜索后，用户退出搜索，再进入页面时不因已处理的旧请求自动展开。
- 点“上传图片识别”后打开选图界面，取消或选图完成后不因旧请求再次打开。
- 用户主动再次点击时仍能正常搜索或选图。
- 搜索与选图分别消费；处理一个请求时不能误删另一个尚未处理的新请求。
- 离开目标页面时不把一次性操作留待用户之后返回页面再执行。
- 请求消费只处理入口触发，不改变搜索内容、图片识别或入库流程。

**操作例子：** 点击上传图片识别 → 相册打开 → 取消 → 离开并返回日程页。预期相册保持关闭，直到用户再次主动点击。

### 2. 震动开关修复

**实施前：** 已有 `hapticFeedbackEnabled` 和“触感反馈”设置。明确传入设置的组件已受控；无参数 `rememberAppHaptics()` 读取 `LocalAppHapticsEnabled`，默认值为 `true`。偏好设置页已有局部提供，但主界面和悬浮窗缺少统一根级提供，部分底栏、菜单等交互仍可能震动。

**fork 的处理：** 在 `MainActivity` 根部提供真实设置；悬浮窗是独立窗口，另行提供同一开关。

**后续预期：**

- 复用已有开关，不新增第二个震动开关。
- 主界面、底栏、菜单、应用弹窗和悬浮窗中的应用触感读取一致的设置。
- 设置改变后，已显示的主界面和悬浮窗也更新，不要求重启。
- 检查相关直接触感／震动调用是否绕过开关，补齐实际遗漏。
- 本项作用于应用交互反馈；日程提醒的通知震动及系统键盘反馈仍按各自设置处理。

**操作例子：** 关闭“触感反馈”后，切换底栏、长按菜单、操作悬浮窗不再产生应用交互震动；重新开启后恢复。

### 3. 日历视图记忆

**实施前：** `calendarViewName` 使用 `rememberSaveable`，已有页面状态保存与恢复，但没有日历视图类型的长期偏好存储。没有恢复状态的新启动默认今日视图，宽屏根据可用模式适配。

**fork 的处理：** 增加“记住日历视图”开关与持久字段，在用户选择视图时写入设置。它没有保留我们的课表和宽屏视图规则，不能直接照抄枚举或布局。

**后续预期：**

- 记忆的是今日／周／月／日程等视图类型，不包含上次选中的日期或滚动位置。
- 持久设置与现有页面状态恢复各司其职；旋转、临时切页和从后台返回时，不反复套用启动规则导致跳视图。
- 保留当前手机与宽屏的可用模式，并处理课表模块关闭等情况。
- 区分用户主动选择和系统因布局／模块变化执行的临时回退，避免临时回退随意覆盖用户偏好。
- 设置读到旧值、未知值或当前不可用模式时安全回退，不崩溃、不清理用户数据。

当前源码中的视图范围：

| 布局 | 可用视图 |
| --- | --- |
| 手机单栏 | 今日、周、月、日程 |
| 宽屏双栏 | 周、月、课表；课表受模块开关约束 |

**操作例子：** 启用记忆后，用户主动切到月视图，结束应用并重新启动，日历恢复月视图。上次选中的是哪个日期不属于本项的长期记忆范围。

### 4. 默认启动视图设置（暂缓）

用户于 2026-10-07 明确：默认启动视图先不做。本项移出当前实施范围，不新增默认日历视图字段、选项或设置页面。

已有 `homeStartPageKey` 和首页“默认启动页”功能保持当前行为。日历视图记忆仍在计划内；关闭记忆、没有历史值或历史值不可用时，按现有布局／模块规则确定起始视图。

本轮按已说明的实施假设默认开启“记住日历视图”。旧配置缺少新字段时安全使用今日／宽屏周视图作为初始值；后续主动选择才产生长期偏好。关闭记忆后的全新启动沿用原始规则。

## 五、下一代随口记方向与分阶段范围

### 已讨论的产品方向

1. **识屏收藏：** 在抖音、哔哩哔哩、公众号、小程序内容页等场景，截图并尝试获取当前内容原链接，上传截图供 AI 分析，收藏到随口记。发现日程／取件码时询问是否创建对应记录，避免抖音聊天记录等页面丢失识别能力。
2. **普通识屏：** QQ、微信聊天、短信等场景，沿用日程／取件码截图识别用途。微信内的公众号、小程序和聊天需结合页面信息判断，不能只按包名分流。
3. **分享兜底：** 软件支持系统分享时，可将链接、选中的文字或图片分享到随口记。没有链接也应保留用户分享的文字，长按 → 全选／选择片段 → 分享即可满足文字收藏。
4. **原内容回跳：** 有原链接的随口记，在详情页底部 toolbar 右侧单独显示圆形“→”按钮，用于打开原内容。
5. **文件夹：** 允许创建文件夹；顶部“全部删除”按钮替换为 list 按钮，用于创建和选择文件夹、筛选列表。
6. **默认列表：** 默认显示全部随口记，不记忆上次文件夹筛选；退出后重置筛选与选择状态。
7. **多选管理：** 长按条目由原浮动操作卡改为进入选择模式；选择模式下底部显示“移动至”“删除”工具栏。

上述为产品方向，分阶段实现。用户目前确定先保留基础改善和文字分享，链接获取方式另行讨论；AI 摘要明确留到后续，不一次完成所有功能。

用户后续已确认：单层文件夹、一条记录一个文件夹；详情返回保留上一级筛选，离开随口记模块后恢复全部。升级范围与维护规则见 [随口记升级](quickmemo-upgrade.md)。

### 第一阶段文字分享的行为

- 在系统分享菜单提供“保存到 Will do 随口记”文字目标，支持纯文字及包含链接的分享文案。
- 完整保留实际收到的文字和换行。没有链接不是失败条件；此阶段链接先作为正文的一部分保存，不要求独立来源字段或跳转按钮。
- 保存成功后提示完成并返回原软件，不要求打开主界面或先选择文件夹。
- 复用现有图片随口记入口和现有随口记存储，不导入另一套闪记／便签数据模型。
- 分享路径先做纯保存，不自动生成摘要，也不因为收藏了一段文字就后台触发日程候选分析；既有其他入口的识别行为保留。
- 当前 `QuickMemoFacade.createTextMemo` 对非空正文会调用 `analyzeTextForSuggestions`。实施时需要在统一创建能力／对应策略中明确分享来源的行为，不能直接调用现有默认路径后误以为只是保存，也不能由分享 UI 直接写 DAO。
- 按软件实际提供的系统分享数据处理；优先兼容文本 `ACTION_SEND`，选中文字的 `PROCESS_TEXT` 是否同时接入按实际目标与入口设计确定。
- 用户选中的文字可能仅是文章片段；接收端保存提供的原文，不凭片段宣称已保存整篇文章。

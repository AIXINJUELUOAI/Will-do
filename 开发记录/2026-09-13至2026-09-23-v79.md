## 1. 记账从预览数据接入真实业务

### 账单管理与统计

- 记账页面接入真实账单，日、周、月摘要、图表与首页金额不再使用写死的示例流水。
- 支持手动新增、编辑和软删除，统一经入库契约保存；编辑保留原来源、交易身份和核对状态。
- 浮动加号点击新建，长按打开导入/导出菜单；条目侧滑提供编辑、删除，沿用公共圆角操作背景。
- 新建默认支出，分类按收入/支出切换；金额使用数字键盘，名称为空时可用分类名称，非法金额不能保存。
- 优化金额、分类、更多字段和保存操作的布局，以及键盘、大字体、侧滑按钮与金额之间的空间。
- 后续将记账顶部切换文案精简为“日 / 周 / 月”，去掉“视图”二字。

### 文件导入（9 月 16 日及后续补齐）

- 核对 AutoAccounting、Veri Fin、double-entry-generator、小遥账单等参考项目的实际能力和许可，保留 [调研记录](../docs/accounting-reference-research.md)；没有把源码可见或免费误判为许可兼容。
- 独立实现 `AccountingFileParser`，支持微信 CSV/XLSX、支付宝 CSV，不为文件解析引入独立入库流程。
- 兼容动态表头、常见编码、Excel 日期系统、共享/内联字符串；错误行保留原始行号。
- 系统文件选择后先本机解析和预览，确认才入库；取消不保存，重复导入沿用稳定身份去重。
- 手动编辑过的记录不会被再次导入覆盖；已软删除记录不会因重导入复活。
- 未完成、失败和关闭交易跳过；中性交易不计收支，需核对的退款状态及外币记录排除在确认收支之外。
- ZIP 外层包需先解压，不支持旧 XLS 和加密表格；没有实现汇率换算或自动退款抵扣。
- 用户已反馈账单导入正常；该反馈不等于所有文件格式变体都经过真机测试。

### 收支建议与账单备份

- 收支建议改为本地分析真实周期数据，覆盖购物、餐饮、外卖、小额累计、大额支出、同期变化、转账、报销及空态等文案。
- 多条建议按固定优先级点击切换，不自动轮播；只使用已确认人民币收支，排除未来、待确认和不计收支记录，不调用 AI。
- 比较门槛、金额阈值等集中登记到 `ConfigCatalog`；同期比较采用相同的已过天数，不把已记录数据当作用户完整流水。
- 独立 JSON 账单备份包含已保存账单及关联截图，不含待确认草稿；恢复采用追加和去重，不覆盖编辑结果、不复活已删除记录。
- 账单导入导出不等同于 WebDAV 双向同步；当前 WebDAV V2 仍主要覆盖日程与随口记。

## 2. 统一识别、入库与去重

- 截图和图片统一走多模态，移除独立 OCR 链路和旧文本 AI 配置模式；旧配置迁移优先保留已有多模态凭据。
- 文字与语音转写能力仍保留，按现有识别模式策略使用 AI、日程正则或回退流程，不把“移除旧文本模型配置”理解为删除文字输入。
- 统一模型结果采用 `events` 与 `bills`；取件仍属于事件分类，不另建独立数组或账单 AI 路由。
- 主动识别的正常账单自动保存，反馈采用实际新增、重复与待确认结果，不把模型候选数量当成入库数量。
- 明确重复跳过，疑似重复及异常候选暂存；“仍然计入”复用现有确认入口，重复点击不能多次新增。
- 去重结合金额、时间、名称及有依据的交易号；不同真实交易号不能仅因同金额同分钟被直接合并。
- 图片账单和草稿保存独立原图路径，详情、编辑和确认后仍可查看。旧账单无原图的不补造；完全重复且无新增/草稿时清理本次无用图片。
- 主动文字缺少时间可以采用当前时间；历史详情与退款必须使用有依据的交易时间，不能随意补成现在。
- 退款实际到账后新增收入，原支出保留；原付款时间和原交易号不能直接替代退款到账时间及独立退款身份。
- 提示词协议迭代至 v15，迁移旧协议块时保留自定义正文；对完成状态、单笔详情、退款及时间依据增加约束。

主要入口继续使用 `RecognitionApi → IngestCommandApi → AccountingRepository`，没有允许 UI 或系统接收器直接写 DAO。

## 3. 无障碍自动记账与支付页面适配

### 页面、事件和局部节点三类证据

- 自动记账默认关闭，开启后仍要求无障碍服务可用及多模态配置齐全；无障碍截图识别会调用模型。
- 初始页面树入口要求支付完成信号和金额，页面稳定后截图；随后根据微信空树诊断补充支付会话成功事件入口。
- 微信统一支付承载页会话不再要求先经过好友转账页面，使扫码等共享承载页的路径可以复用；仅打开支付页面不算成功。
- 增加当场读取事件 `source` 的局部内容，不把系统事件或节点持有到延迟协程中。
- 单笔详情等待金额与真实时间等关键内容就绪，避免只看到标题、加载页或导航按钮便截图。
- 事件、候选与截图前后按实际前台包和窗口 ID 校验，后方聊天页的迟到事件不能覆盖前台详情身份。
- 保留防抖、信号有效期、最短请求间隔、同页抑制和全局识别互斥；空树刷新不能不断取消已就绪候选。
- 聊天页、编辑状态、列表页、取消或失败交易不自动识别；无法取得有效证据时跳过，不用连续截图和模型调用试探。

### 付款、退款与收款汇总（9 月 17—19 日持续适配）

- 根据用户诊断补齐微信付款码局部成功节点、支付宝成功局部节点，以及拼多多调起微信/支付宝收银台的已确认上下文。
- 对收银台中提前出现商户单号的情况，避免仅凭单号将支付现场误锁为历史详情；仍需完成状态和金额。
- 扩展转账过期退回、原转账退还、购物退款及独立退款单详情，区分顶部原支出与实际退款字段。
- 微信退款单增加对应详情标记；支付宝独立退款账单在完整证据组合下允许使用创建时间，并在备注注明依据，不宣称该时间就是精确到账时刻。
- 按用户选择允许微信收款小账本、支付宝经营分析的明确汇总页：主合计作为一笔收入，缺少时分时按统计日期零点处理。
- 汇总识别不拆分逐笔、不计算差额、不按日覆盖；与逐笔账单可能重叠，保留提示和现有去重边界。
- 购物应用纳入诊断采集范围，不等于它们的全部页面已开放正式自动记账。

完整页面证据、阶段日志和联测清单见 [自动记账适配与验证](../docs/automatic-accounting-testing.md)。本记录不复述支付正文或用户诊断包内容。

## 5. 微信发红包与通知优先（9 月 21 日）

- 无障碍发红包新增短时会话：准备页提交后，在确认页稳定时暂存截图；同会话收到成功“已发送”信号才调用多模态。
- 金额必须来自清晰确认截图，不从编辑页、加载页、聊天返回页或松散金额缓存猜测。
- 取消、失败、超时、离开微信、关闭开关或服务中断会清理暂存；截图过晚或不可读时不强行记账。
- 只记录发送成功的支出；名称缺失时用“微信红包”，时间取成功信号接收时刻。此项不代表所有微信版本和领取红包场景通过。
- 通知与短信记账开启且权限满足时，现场截图进入 AI 前最多等待 1500ms，让已成功本地入库的同源通知优先。
- 仅消费符合来源、方向、时间窗和可用金额证据的唯一回执；疑似重复、待确认、失败、短信及历史详情不用于抑制现场 AI。
- 空树或红包截图无法本地读取金额时，唯一同源支出回执仍是短时启发式；超时后两路并行继续依赖最终去重，不能宣称完全消除所有重复调用。
- 已补会话、取消、过期、旧回调和通知匹配回归；实际支付效果仍待 Release 联测。

## 6. Agent 记账接口

- 增加 `createBill / getBill / queryBills / updateBill / deleteBill / getBillSummary`，官方 Provider 与第三方广播共用 `AgentAccountingService`。
- 读取依赖 `AccountingApi`，新增、修改和删除经统一入库契约，不开放 DAO 直写。
- 新增返回 `SAVED / DUPLICATE / SUSPECTED_DUPLICATE / PENDING`；后两者保留草稿，不计入确认收支。
- 输入金额采用十进制元字符串，输出整数分，账单时间为 Unix 毫秒；新增当前只支持人民币，汇总按币种分组。
- 汇总不受列表分页截断；局部修改保留来源、交易号、去重身份和截图。
- 补齐仓库内 Agent 协议与记账说明，仍以 `getCapabilities.methods` 判断能力；没有扩大第三方附件和文件访问权限。
- 既有技术记录提到 Awill 调用端同步接入 `willdo_bills`；本次只核对 Will do 工作区，不将外部仓库状态重新标为验证通过。

## 7. 首页日程视图、搜索与动画

### 日程视图基础能力

- 今日页增加日、周、月之外的“日程”视图，按日期组合星期、日期、农历、当天支出和日程卡片。
- 同日日期与摘要只显示一次，支出可跳转当日账单；首页日/周/月的金额摘要也按选中日统计。
- 复用重复实例展开、例外和子事件处理；无限重复分段展开，末端继续拖动并松手后加载未来七天，不因单纯滑到末端反复加载。
- 支持正向、反向日期排列，同一天内部仍按时间递增；追加数据保留可见业务行与像素偏移。
- 区分真正无后续实例和“本段七天为空但仍有更远实例”，加载提示居中并随手势变化。
- 今日搜索覆盖全部未归档日程的标题、描述和地点；各视图保留独立滚动位置，清空搜索恢复原状态。
- 选中日期块接入日/周/月与日程列表之间的共享形变，调整位置、尺寸、颜色和圆角衔接，保留搜索离场快照。

### 9 月 23 日的最终显示规则与选中跟随

- 开发者增加“完整 / 仅日程”显示模式，默认“仅日程”。
- “完整”补齐已展示日期范围内的空日期；“仅日程”只保留有日程的日期，只有账单的日期不再单独撑出一组。
- 搜索结果不填充空日期。旧技术文档中“仅有账单也显示”的描述属于此前阶段，不是当前默认行为。
- 手机列表滑动时先保留当前选中日期；其退出可见区域后，沿滚动方向将选中转给边缘可见日期。
- 补充同日多条长列表的日期锚点处理，以及自动选中后防止状态更新把列表滚回去的保护，为返回日视图保留连续动画锚点。
- 编译和单测不能替代实际设备的手势与动画验收，验证参考 [首页日程视图清单](../docs/home-agenda-testing.md)，显示规则以本节后续调整为准。

## 12. 无障碍间歇失效：保留日志并自查（9 月 23 日）

### 已知现象与判断边界

- 用户转述的故障诊断中，未收到微信/支付宝事件，多次前台窗口为空，截图请求为零；重新开关无障碍后，原微信账单详情路径恢复。
- 故障位于采集入口，尚未走到截图识别，不能据此增加支付关键词或归因于模型。
- 期间仍有桌面、系统和自身应用事件，不能直接判断整个无障碍服务完全断连。
- 重开恢复不证明具体根因；仍需区分服务配置、生命周期、窗口读取和系统/微信事件投递状态。

### 基础日志与主动诊断

- 沿用开发者“开始支付采集诊断 / 结束并导出支付诊断”，不另加入口。
- 基础 `WillDoAccessHealth` 日志覆盖连接、中断、解绑、销毁、配置更新、任务异常和事件恢复间隔，只记录状态，不打印支付正文、金额、联系人或单号。
- 基础日志遵循原自动记录开关、保留天数和容量限制，不新增无限保存策略。
- 手动诊断会话内每 1500ms 独立检查实际监听配置、服务状态、事件计数/间隔、任务状态及窗口身份，不依赖支付事件或截图循环。
- 开启诊断前保存原配置状态，避免临时诊断标记掩盖现场；异常读取与空窗口分别记录。
- ZIP 附带 `service-health-before.log`、`service-health-final.log` 和会话 `service_health`，历史日志读取失败不阻止本次详细诊断。
- 应用内实例存在、系统启用列表包含服务，都不单独证明事件通路健康。
- UI 树和截图仍仅在主动诊断会话采集；诊断期间暂停正式无障碍自动识别，结束或超时后恢复。

### 自查后实施的修正

- 配置读取/更新异常不再打断设置监听，或阻止服务解绑/销毁时的后续清理。
- 同一实例重复连接时，保留原基础 flags，不将诊断临时标记固化为长期配置。
- 旧服务实例退出时，不清除已经指向新实例的全局引用。
- 增加任务异常类型日志，以及诊断初始化期间连接已经变化的检查。
- 未加入盲目自动重启、强制开关无障碍、放宽截图范围或模型兜底试探；修正后保留新增诊断。
- 这些属于有代码依据的健壮性修正，尚不能认定就是此次间歇失效的根因，也未获得修复后的真机结论。

下次复现应先保留故障：开启诊断 → 回到原微信账单详情 → 导出故障包 → 再手动重开无障碍，并采集恢复后的同一路径作对比。服务完全断开、无法开启诊断时先导出应用日志。
